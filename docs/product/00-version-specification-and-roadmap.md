# 精投助手版本规范与路线图

## 1. 文档目的

本文件是精投助手产品版本边界、范围归属、阶段准入和范围变更的唯一事实来源，回答以下问题：

1. 当前 Demo、求职作品版 V0.1、产品验证版 MVP、正式版 V1.0 和后续版本分别解决什么问题。
2. 一项能力应在哪个版本交付，优先级和完成标准是什么。
3. 求职作品版达到什么条件可以用于投递，产品 MVP 达到什么条件可以开始用户验证，V1.0 达到什么条件可以公开运营。
4. 需求新增、延期、拆分或跨版本移动时，如何完成评审并同步其他文档。

PRD 负责定义产品目标与需求；本文件负责定义需求在哪个版本实现。两者冲突时，产品目标以 PRD 为准，版本归属以本文件为准。

## 2. 版本定义

| 阶段 | 定义 | 核心目的 | 目标用户 | 发布方式 |
|---|---|---|---|---|
| 当前 Demo | 已存在的简历—JD 六维匹配实现，是迁移起点而非目标版本 | 验证已有技术能力和识别可复用模块 | 内部人员 | 不作为目标产品发布 |
| V0.1 求职作品版 | 当前第一个必须实现的版本 | 在有限周期内，用少而深的功能证明开发者懂 AI 产品、Agent、评测与落地 | HR、AI PM 面试官、技术面试官 | 可访问作品 Demo + 简历项目材料 |
| 产品 MVP | 最小用户验证产品 | 验证“证据驱动的岗位简历优化”是否具有真实用户价值 | 小规模种子用户、受控内测用户 | 邀请制或灰度发布 |
| V1.0 正式版 | 首个可公开运营版本 | 在核心价值成立后，提供安全、稳定、完整且可持续使用的产品 | 公开用户 | 正式公开发布 |
| V1.x 商业化版本 | 正式版后的持续增强 | 建立会员权益、长期留存和运营增长能力 | 免费用户与付费用户 | 持续迭代 |
| V2.0 及以后 | 产品边界扩展 | 扩展岗位、求职阶段或智能能力 | 待产品验证 | 另行立项 |

当前执行顺序为：`当前 Demo → V0.1 求职作品版 → 产品 MVP → V1.0 正式版 → V1.x`。

V0.1 的首要成功标准是有效展示能力，而不是覆盖完整商业产品范围。产品 MVP 才开始承担账号、长期数据资产和种子用户验证。“正式版”也不表示包含所有设想功能；V1.0 仅包含公开运营所必需的完整能力。

## 3. 版本目标

### 3.1 V0.1 求职作品版要证明的能力

V0.1 必须让招聘方在短时间内获得以下判断：

1. 开发者理解生成式 AI 的事实失真、黑盒建议和不可稳定复现等产品风险。
2. 开发者能够把目标、状态、工具、动态分支、人工确认、审核循环和停止条件组织成可运行的 Agent 工作流。
3. 开发者会建立标准案例、质量指标、安全护栏和回归方法，而不只凭主观感受调 Prompt。
4. 开发者能够把 AI 嵌入“发现问题—修改—验证效果—继续优化”的真实用户闭环。
5. 开发者能够区分确定性规则、模型语义判断和必须由用户确认的事项。
6. 开发者能在个人时间和资源约束下主动控制范围，并交付稳定、可快速体验的 Demo。

V0.1 的核心叙事是：

> 精投助手不是黑盒评分或一键代写工具，而是一个让简历修改依据可追溯、过程可验证、结果能经受面试追问的 AI 求职教练。

### 3.2 产品 MVP 要验证的问题

产品 MVP 必须能回答：

1. 用户是否愿意补充并确认真实职业证据，而不是只获取一次性改写结果。
2. 证据地图是否能帮助用户理解岗位要求、已有证据与真实能力缺口。
3. 逐条修改是否比整份一键生成更容易获得用户信任和采纳。
4. 用户能否产出一份真实、针对当前 JD 且能经受面试追问的简历内容。
5. 已确认的证据能否在第二个岗位版本中复用并减少重复输入。
6. 用户是否愿意在一个典型求职周期内持续返回使用产品。

### 3.3 V1.0 要解决的问题

V1.0 必须在 MVP 价值成立的基础上解决：

1. 公开用户的稳定访问、账号安全、数据隔离与跨设备使用。
2. 完整的数据生命周期、通知、恢复、导入导出与隐私管理。
3. 可持续的 AI 质量、成本、降级、监控和运营能力。
4. 更完整的简历交付、版本管理和产品自助使用体验。
5. 公开发布所需的客服、风控、指标、合规和故障响应闭环。

## 4. 范围标记规范

每项需求同时使用“目标版本”“优先级”和“状态”三个字段，不得只写“后续支持”。

### 4.1 目标版本

| 标记 | 含义 |
|---|---|
| `V0.1` | 必须在求职作品投递和演示前交付 |
| `MVP` | V0.1 可暂不交付，但必须在产品内测前交付 |
| `V1.0` | 产品 MVP 可暂不交付，但正式公开发布前必须交付 |
| `V1.x` | 正式版后的增量能力 |
| `V2+` | 需要重新验证或另行立项的扩展能力 |
| `TBD` | 信息不足，尚未完成版本归属评审 |

### 4.2 优先级

| 标记 | 定义 | 处理规则 |
|---|---|---|
| `P0` | 缺失会破坏核心闭环、安全、事实可信或版本发布条件 | 不得带缺陷发布 |
| `P1` | 显著影响完成率、体验或运营效率，但存在可接受替代方案 | 原则上随目标版本交付 |
| `P2` | 增强体验或效率，不影响目标版本成立 | 可按容量延期 |

`P0` 不等于某个特定版本。例如 Agent 主闭环属于 `V0.1/P0`，账号所有权校验属于 `MVP/P0`，完整公开运营风控可以属于 `V1.0/P0`。

### 4.3 需求状态

| 状态 | 含义 |
|---|---|
| `proposed` | 已提出，尚未评审 |
| `approved` | 已确认进入目标版本 |
| `in_progress` | 已进入设计或开发 |
| `verified` | 已通过对应验收 |
| `deferred` | 经评审延期并记录原因 |
| `removed` | 经评审取消，不再计划实现 |

## 5. 版本范围总表

| 能力域 | V0.1 求职作品版 | 产品 MVP | V1.0 正式版 | V1.x 及以后 |
|---|---|---|---|---|
| 核心目标 | 展示 AI PM、Agent、评测与落地能力 | 验证真实用户价值和持续使用 | 支持公开稳定运营 | 商业化和长期增长 |
| 账号与身份 | 不新增账号；演示数据或单次会话状态 | 一种轻量登录方式；持久保存前登录 | 多种登录方式、完整账号中心、异常登录与找回 | 新身份关系按需立项 |
| 数据保留 | 仅满足演示和本次任务，不建设长期资产 | 免费账号最后有效活跃后保留 30 天 | 自助恢复、完整通知与数据生命周期后台 | 会员延长至 180 天、1 年或长期 |
| 证据能力 | 当前任务内的证据检索、追溯、追问和事实审核 | 长期职业证据库、确认、深挖、复用和标准导入导出 | 搜索、版本历史、来源管理和迁移兼容 | 长期职业档案和第三方迁移 |
| JD 与诊断 | JD 解析、缺口判断、健康度体检 | 岗位方向、核心要求、证据地图和任务优先级 | 企业背景、多 JD 对比和更强隐性要求识别 | 岗位市场洞察 |
| 修改体验 | 段落级候选生成、事实审核、修改效果验证闭环 | 完整修改工作台、教学层级和岗位版组装 | 版本历史、批量操作、高质量交付 | 协作和更多自动化工作流 |
| Agent | 一个边界清晰、可观察、可恢复的简历优化 Agent | Agent 接入长期证据和多岗位任务 | 模型路由、灰度、线上监控和成本治理 | 个性化及经评审的新型能力 |
| AI 评测 | 标准案例集、关键质量指标、安全护栏和回归结果 | 扩大评测集并连接内测反馈 | 持续评测、发布门槛和线上质量监控 | 精细化实验与治理 |
| 展示 | 无输入的一键演示、架构说明和典型案例 | 真实用户完整流程 | 公开产品自助体验 | 增长和商业化展示 |
| 数据安全 | 不泄露演示或测试数据；敏感信息最小化 | 账号隔离、最小权限、隐私告知和主动删除 | 加密、审计、异常访问监控和完整合规 | 随业务规模增强 |
| 商业化 | 不收费、不建设权益系统 | 不收费；仅预留套餐、权益和到期字段 | 具备接入商业化的基础 | 会员、订单、支付和续费 |

## 6. V0.1 求职作品版已批准范围

### 6.1 必须完成：V0.1/P0

#### PF-001 证据驱动的简历优化 Agent

- 将 JD 解析、证据检索、缺口诊断、动态追问、候选生成和事实审核组织为有状态工作流。
- 明确 Agent 的目标、输入、任务状态、可用工具、动态分支、人工确认点和停止条件。
- 每条建议展示用户可验证的理由链：JD 原文、简历事实、缺口类型和修改理由。
- 证据不足时追问；用户确实没有相关经历时标记能力缺口，不强行生成。
- 候选内容必须通过事实审核后才可进入用户确认。
- 不展示或声称展示模型私有思维链，只展示证据引用和可验证理由摘要。

完整流程和业务规则见 [V0.1 证据驱动的简历优化 Agent 模块规格](./modules/portfolio-resume-agent.md)。

#### PF-002 AI 评测与安全护栏

- 建立固定、可重复执行的标准案例集。
- 至少测量无依据事实率、错误归因率、Schema 合法率和任务完成率。
- 对未确认数字、团队成果错误归为个人成果、缺少证据引用等风险进行阻断或降级。
- 保留典型失败案例、修复方式和回归结果。
- 为 LLM 结构异常、超时和不可用设计验证、重试和可解释降级。

V0.1 采用“候选生成—基础校验—一次独立事实审核”的简化运行时护栏；审核结果统一为 `passed`、`warning`、`blocked` 和 `unavailable`。用户确认的估算数字可在保留限定词和风险标记时使用，AI 推测或未确认数字必须阻断。用户修改 AI 候选后不自动重新审核，也不继续标记为 AI 已验证。

完整流程和业务规则见 [V0.1 AI 评测与安全护栏模块规格](./modules/ai-evaluation-and-safety-guardrails.md)。

#### PF-003 修改效果验证

- 用户可以连续修改和自动保存；认为本轮修改完成后，点击“完成修改并验证”统一运行 PF-003。
- 展示修改前后文本 Diff、证据覆盖变化、安全状态、改善点、剩余问题和下一步。
- 修改效果使用 `improved`、`unchanged`、`regressed` 和 `tradeoff`；`tradeoff` 展示为“有改善，也有新问题”。
- PF-002 安全状态独立判断，只有 `passed` 显示“已验证”；`blocked` 不阻止用户保存和使用，但只能以有风险状态完成。
- 分数仅作辅助信息，不作为唯一结论或任务完成条件。
- 保留修改前快照和用户当前文本；验证失败不得覆盖或丢失任一版本。
- 一次验证只调用一次语义评估，确定性 Diff、Schema、数字和引用检查由程序完成。
- 每次主动验证追加不可变记录；页面默认展示最新结果，同时保留任务最初原文。

完整流程和业务规则见 [V0.1 修改效果验证模块规格](./modules/modification-effect-validation.md)。

#### PF-004 预计算引导演示

- 招聘方无需注册、输入简历、输入 JD 或等待实时模型即可进入演示。
- 使用固定、脱敏、版本化的预计算快照，复用 PF-001、PF-002 和 PF-003 的真实状态结构。
- 按“JD 要求—简历事实—缺口判断—动态追问—事实确认—候选审核—修改验证”回放关键闭环，不只跳转到静态结果页。
- 30 秒内看到第一处明确价值；完整流程可以继续查看。
- 明确标记示例数据和预计算结果，不伪装实时 AI 调用。
- 演示不写入普通分析历史或真实业务指标，支持重新开始和进入真实分析。

完整流程和业务规则见 [V0.1 预计算引导演示模块规格](./modules/guided-demo-mode.md)。

### 6.2 应该完成：V0.1/P1

#### PF-005 简历健康度体检

- 作为不依赖 JD 的独立入口，检测模糊动词、量化缺失、贡献模糊和结构完整性。
- 明确区分确定性规则、模型语义判断和需要用户确认的结果。
- 输出问题位置、判断依据、风险级别和可执行建议。
- 体检结果可作为后续 Agent 优化任务的输入，但不要求建设长期证据库。

### 6.3 有余力再完成：V0.1/P2

#### PF-006 面试预测与多版本改写

- 面试预测基于已识别的 JD—简历缺口生成，不做与证据无关的泛化题库。
- 多版本改写可以提供稳妥版、强化版或数据驱动版，但所有版本共享同一事实边界。
- 可只实现其中一个子功能；缺失不影响 V0.1 完成和求职投递。

### 6.4 V0.1 明确不包含

- 账号、登录、会员、支付和运营后台。
- 长期职业证据库、多岗位版本管理和跨设备同步。
- 证据库导入导出、长期数据保留和到期恢复。
- 完整 Word/PDF 排版、海量模板和自动投递。
- 非产品岗位的完整适配。
- 复杂多智能体系统、自训练或微调模型。
- 为了展示“Agent”而引入没有必要的多 Agent 协作。
- 没有真实用户时搭建完整增长埋点体系。

### 6.5 V0.1 求职交付物

V0.1 不只交付代码，还必须形成：

1. 一个稳定、无需输入的一键演示。
2. 一张说明目标、状态、工具、分支、审核和停止条件的 Agent 工作流图。
3. 一份包含指标、样本、失败案例和回归结果的 AI 评测报告。
4. 一份简洁的产品案例说明，讲清用户问题、关键取舍和人机边界。
5. 三条基于真实实现和测量结果撰写的简历项目描述。

## 7. 产品 MVP 已批准范围

### 7.1 产品 MVP/P0

- 轻量账号体系以及所有用户数据接口的服务端所有权校验。
- 游客数据与注册账号数据的明确边界；游客不得作为长期证据库身份。
- 简历文本、PDF、DOCX、TXT 导入和解析确认。
- 职业证据库、经历卡、技能卡、事实来源和确认状态。
- 至少一种代表经历深挖路径；是否强制完成两段仍为待决策项。
- JD 输入、OCR 文本确认、岗位方向和要求分析。
- 要求—证据地图、缺口分类和有优先级的修改任务。
- 单条修改工作台、事实追问、建议生成、用户编辑与事实复核。
- 岗位简历内容组装、复制、保存和投递前检查。
- 无依据事实、错误归因和未确认数字的发布阻断。
- 免费账号数据按最后有效活跃时间保留 30 天。
- 到期提醒、用户主动删除以及与实际行为一致的隐私说明。
- 证据库标准 JSON 导出、可阅读 Markdown 导出及标准格式重新导入。
- 导入预览、合并和取消；导入失败不得覆盖或破坏已有证据。
- 核心漏斗、AI 事实质量和错误恢复埋点。

### 7.2 产品 MVP/P1

- 游客可在登录前查看产品并完成一次有限的基础体验。
- 到期前多次站内提醒。
- 导出包的格式版本说明和基础完整性校验。
- 第二个岗位版本的证据复用提示。
- 用户反馈入口和问题数据的最小化采集。

### 7.3 产品 MVP 明确不包含

- 面向非产品岗位的完整适配。
- 完整 Word/PDF 排版、海量简历模板和自动投递。
- 求职信、岗位搜索和完整面试训练。
- 手机号、邮箱和多个第三方平台全部同时登录。
- 支付、订单、续费和正式会员套餐。
- 长期或永久在线保留免费用户数据。
- 第三方证据库格式导入。
- 多人协作、企业组织和专家工作台。
- 自训练模型、复杂多智能体系统或无确认的一键整份重写。

## 8. 账号、保留与迁移专项决策

### 8.1 已确认产品决策

| ID | 决策 | 目标版本 | 优先级 | 状态 |
|---|---|---|---|---|
| VER-001 | 职业证据库上线时必须具备账号体系，不继续以设备 ID 作为长期身份 | 产品 MVP | P0 | approved |
| VER-002 | 免费账号数据默认按最后有效活跃时间保留 30 天 | 产品 MVP | P0 | approved |
| VER-003 | 用户可以导出并重新导入证据库，用于下次求职或跨设备迁移 | 产品 MVP | P0 | approved |
| VER-004 | 数据结构预留差异化保留周期和会员权益，不在产品 MVP 内收费 | 产品 MVP | P1 | approved |
| VER-005 | 后续可延长保留期限或将长期保存作为会员权益 | V1.x | P1 | proposed |

### 8.2 产品 MVP 最小实现规则

1. “最后有效活跃”至少包括编辑证据、确认事实、创建或修改岗位版本、完成任务以及导入数据；仅打开页面是否续期需在埋点评审时确定。
2. 过期前必须在产品内明确展示到期日期并提醒导出；邮件等外部提醒是否进入 MVP 由通知成本评审决定。
3. 到期后的恢复窗口建议为 7 天，当前属于待技术和隐私评审项；未确认前不得在用户文案中承诺。
4. 主动删除与自动到期是两种不同流程。用户主动删除时，不得以“默认保留 30 天”为由继续提供正常访问。
5. 导出文件必须包含 `schemaVersion`、`exportedAt` 和数据对象说明，不得包含密码、令牌、内部提示词或仅供系统使用的敏感日志。
6. 导入必须先校验格式和版本，再展示预览；默认采用“合并”，不得静默覆盖已有确认证据。
7. 保留周期和账号权益必须配置化，不能散落为代码中的固定判断。

## 9. V1.0 正式版准入范围

V1.0 的详细需求在 MVP 验证后冻结，但公开发布前至少必须具备：

- 完整账号中心、账号找回、注销和跨设备一致性。
- 稳定的数据到期提醒、恢复、删除和审计流程。
- 导入导出历史版本兼容及更完整的数据归档。
- 可公开承诺的服务稳定性、监控、告警、限流和降级方案。
- AI 质量评测集、发布门槛、回归机制和线上质量监控。
- 高质量简历交付能力，具体包含 PDF、Word 还是其中一种，待 MVP 用户研究后确认。
- 清晰的用户协议、隐私政策、第三方 AI 数据说明和客服入口。
- 公开运营所需的反馈处理、事故响应和后台工具。
- 经真实用户数据验证后冻结的核心指标门槛。

以下能力不因进入 V1.0 自动成立，仍需单独评审：会员收费、自动投递、非产品岗位、完整面试训练和第三方证据库迁移。

## 11. 版本完成定义

### 11.1 V0.1 求职作品版完成

同时满足以下条件才可用于简历投递和作品演示：

1. PF-001 至 PF-004 全部达到 `verified`。
2. PF-005 未完成不会阻塞投递，但必须明确标记状态；PF-006 不作为完成条件。
3. Agent 工作流真实可运行，不能只是流程图或连续 Prompt 的包装。
4. 预计算引导演示无需注册、无需输入、无需实时 AI 调用，复用真实状态结构并稳定展示 PF-001 至 PF-003 的关键闭环。
5. AI 评测报告包含固定案例、指标结果、失败案例和至少一次回归对比。
6. 关键流程具备自动化测试，失败和降级路径可演示或有测试证据。
7. 简历与作品说明只使用真实实现和真实测量结果，不虚构用户数、准确率或业务收益。

### 11.2 产品 MVP 完成

同时满足以下条件才可称为产品 MVP 完成：

1. MVP/P0 功能全部达到 `verified`。
2. [MVP 验收标准](./09-mvp-acceptance.md)中的发布阻断项为零。
3. 账号隔离、保留、导入导出、删除和恢复规则通过端到端测试。
4. AI 不产生无依据事实、错误个人归因和未确认数字。
5. 核心漏斗和质量指标可被可靠采集。
6. 已明确内测规模、验证周期、成功信号和停止条件。

### 11.3 V1.0 完成

除 MVP 完成条件持续成立外，还必须满足：

1. V1.0/P0 全部达到 `verified`。
2. 稳定性、安全、隐私、监控、客服和事故响应通过发布评审。
3. 数据生命周期实际行为与用户协议、隐私文案完全一致。
4. AI 模型或提示词升级具有离线回归和灰度机制。
5. 公开用户可以自助完成登录、使用、导出、删除和账号注销。

## 12. 范围变更规则

任何新增、删除、延期或跨版本移动必须记录以下内容：

- 需求名称、提出人和提出日期。
- 当前目标版本、建议目标版本和优先级。
- 用户价值或风险依据。
- 对页面、流程、数据、AI、隐私、埋点、测试和排期的影响。
- 替代方案以及不实现的后果。
- 产品、研发、设计、AI 和测试的评审结论。

变更批准后必须同步：

1. 本文件中的版本范围或专项决策。
2. PRD 的范围和非目标。
3. 对应页面、流程、领域模型、AI 或模块规格。
4. 对应验收项与指标。

不得只在会议纪要、聊天记录或开发任务中改变版本范围。
