# 求职作品案例 — 精投助手"证据驱动简历教练"的构建

## 一句话

> 我把"AI 改简历"从不可信的黑盒，做成一个每条建议都可追溯到 JD 原话和用户真实经历、并把"虚构事实"挡在门外、让用户自己决定最终文本的证据驱动简历教练。

## 问题

市面上的 AI 简历工具分两类：模板填空，或把简历丢给大模型"一键重写"。后者有严重且隐蔽的问题：

- **AI 会系统性夸大**。同一个模型，"参与访谈"会被改写成"主导访谈"，"学习 Python"会被改写成"使用 Python"，甚至凭空补一个"访谈 500 位用户"或"营收增长 20%"。
- **用户无法追问**。工具输出"已优化"的文本，但面试官追问"这部分是你做的吗？依据是什么？"时，用户没有答案。
- **没有反馈闭环**。改完不知道改对没有、是否引入了新的事实风险。

作为求职作品，我不想做一个"看起来功能很多"的评分器，而想展示我对 AI 能力边界、信任问题和工作流闭环的理解。

## 决策

围绕"可追溯、可审核、可停止"定下五条关键决策：

1. **AI 只提建议，不替用户决定。** 所有进入候选的事实必须由用户逐条确认；最终文本由用户采用、编辑或拒绝。
2. **硬红线用确定性规则，不用 LLM 黑名单。** 数字、职责、项目状态、证书、技能这些最容易造假的信息，先用可测试的正则+语义抽取规则拦截；LLM 判断不稳定，不能当唯一防线。
3. **独立语义审核。** 确定性检查通过后，再让独立提示词把候选与引用事实做语义比对，阻断"完全无关的自我介绍"混入。审核异常/超时/格式非法一律降级为 `unavailable`，**绝不默认通过**。
4. **"文本变好"和"事实安全"分开算。** 修改效果验证（PF-003）分别输出 `changeOutcome`（改善/持平/回退）与 `safetyStatus`（是否安全），两者独立——文本写得更好不等于事实是安全的。每次验证追加不可变历史记录。
5. **Agent 状态机可崩溃恢复。** 异步分析用原子 claim + 租约 + 心跳续租，进程崩溃后过期任务可恢复，旧 worker 的 token 无法覆盖新 worker 的结果；并发启动被串行化。

## 边界

- V0.1 是单会话求职作品版：无登录、无账号体系，用设备 ID（`X-User-Id`）隔离数据。明确不做证据库、跨设备同步、完整简历自动重写、多版本对比。
- 不展示模型私有思维链，只展示 JD 依据、事实来源和理由摘要。
- 演示模式（GuidedDemo）只回放真实状态快照，不调用实时 AI、不写历史、不进真实统计漏斗。
- 真实简历数据在公开部署前必须完成数据迁移 dry-run 与索引验证，才允许进入生产。

## 实现

- **架构**：前后端分离。Vue 3 + Vant + Vite 前端（hash 路由，8 个页面），Express 5 + Mongoose 9 + MongoDB 后端，DeepSeek 提供解析与语义判断。前端 API 统一携带 `X-User-Id`。
- **Agent 编排**（`server/services/agent/agentOrchestrator.js`）：单一编排器根据会话/任务状态选择工具（`parseJD`、`parseResume`、`matchEvidence`、`assessAnswer`、`draftRevision`、`verifyRevision`、`repairRevision`、`evaluateModification`），工具之间不直接调用。状态迁移只通过编排器入口推进。
- **安全护栏**（`server/domain/agent/guardrails.js` + `pf002Evaluator`）：确定性规则拦截未确认数字、跨用途数字（"20 位用户"→"营收增长 20%"）、职责扩大（参与→主导）、项目状态/证书/技能/学习经验扩大；独立语义审核拦截无最低语义重叠的内容。
- **评测**（`server/evaluations/pf002Cases.js`）：12 个端到端案例真实经过 orchestrator，30 个原子案例执行确定性规则；生成版本化报告，任何红线失败进程退出码为 1。
- **前端响应式重构**：移除 480px 手机壳，按 600/900/1200px 四档断点适配手机/平板/电脑，Agent 工作台电脑端侧栏+主区双栏、宽屏加证据上下文栏；键盘焦点、44px 触控目标、降动效/降透明度/高对比降级、200% 缩放不横向溢出。

## 结果

可复核的自动化证据（全部本地可重跑）：

| 项 | 结果 |
|---|---|
| 后端测试 | 114/114 通过 |
| PF-002 固定评测 | 42/42 通过（12 orchestrator + 30 原子） |
| 前端契约测试 | 15/15 |
| 前端单元测试 | 36/36 |
| Playwright 浏览器验证 | 31 通过 / 8 按设计跳过 / 0 失败（手机 390×844、平板 768×1024、电脑 1440×1000 × 8 路由） |
| 生产构建 | 通过 |

关键能力的可演示证据：

- 同一模型改写时，"牵头制定公司战略并推动营收增长"被正确判为 blocked（`attribution_expansion`），"实现营收增长20%"被正确判为 blocked（`number_context_expansion`）——这两类在修复前都会被误判为通过。
- "完全无关的自我介绍"无法混入候选（`unsupported_claim_semantics`）。
- 用户确认风险内容后进入 `completed_with_risk`，handoff 保留 `verificationStatus=blocked` 与 `riskAcknowledged=true`，系统不把"用户坚持保留"误标为"已验证"。

## 面试讲解建议（30 秒版本）

> "通用 AI 简历工具给你一版改好的文字就结束了。我做的是把'AI 改简历'变成教练式闭环：JD 要求什么 → 你简历里哪段真实经历能支撑 → AI 的改写建议是否越界 → 改完是否真的更安全。我特意用确定性规则加独立语义审核两层防线，把'参与'写成'主导'、把'学习'写成'使用'、甚至编一个 500 位用户这种 AI 常见的夸大行为挡在门外。42 个固定评测用例全部通过，任何一个被误放行构建就失败。"
