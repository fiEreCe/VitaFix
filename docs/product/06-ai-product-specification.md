# 精投助手 AI 产品规格

## 1. 文档目标

定义 AI 任务的产品输入、结构化输出、触发条件、事实边界、用户确认、失败处理、版本追踪和质量评测。本文件不保存生产密钥或完整 Prompt。

## 2. 当前能力与目标变化

当前实现使用 DeepSeek `deepseek-chat`，通过多次独立调用完成 JD 解析、简历解析、六维匹配和单板块重评估；温度为 0.1—0.15，返回 JSON 后由服务层做范围和枚举校验。AI 请求支持最多 2 个并发、网络/429/5xx 有限重试，单次超时 120 秒。

目标 MVP 保留“单模型、多任务、结构化输出”方案，但从评分中心升级为证据中心：

- 保留：解析、结构化 Schema、异步处理、单步重试、任务拆分。
- 降级：整体匹配总分和雷达图，仅作辅助。
- 新增：事实来源、用户确认、证据追问、双表达强度、独立审核、学习反馈。
- 禁止：从关键词补写不存在的经历、数字、技能或职责。

## 3. AI 产品原则

1. AI 解析不是事实确认。
2. 每条生成表达必须引用已确认事实。
3. 证据不足时先追问，无法补充时标记真实缺口。
4. 个人贡献、团队成果、估算数据和项目性质必须明确区分。
5. 生成和审核使用独立调用上下文，避免自我证明。
6. 对用户展示可核验的理由摘要、证据和规则，不展示模型私有思维链。
7. 所有任务记录模型、Prompt、Schema 和规则版本，支持复现和回归。
8. AI 失败只影响当前步骤，不丢失用户已确认数据。

## 4. AI 任务清单

| 任务 ID | 任务 | 触发 | 核心输出 | 用户确认 | 当前基础 |
|---|---|---|---|---|---|
| AI-001 | 简历解析 | 导入文本/文件 | 板块、经历、技能、原文映射 | 必须 | resumeParser 可复用 |
| AI-002 | JD 解析与分类 | 提交 JD | 岗位方向、职责、五类要求、重要度 | 必须 | jdParser 需扩展 |
| AI-003 | 证据检索与匹配 | JD 已确认 | 要求—证据映射、强度、诊断 | 待确认项需确认 | matchAnalyzer 思路可复用 |
| AI-004 | 证据缺口追问 | 存在待确认匹配 | 单个高价值问题、期望事实类型 | 回答必须确认 | 新增 |
| AI-005 | 推荐表达生成 | 事实充分且任务开始 | 稳妥/强化表达、来源、理由摘要 | 必须 | sectionReevaluator 需重构 |
| AI-006 | 三类质量审核 | 候选表达或组装版本变化 | 真实性、相关性、表达问题 | 阻断问题需处理 | 新增 |
| AI-007 | 教学反馈与练习评估 | 用户独立提交文本 | 缺失项、原则反馈、参考版本 | 参考版本按需 | 新增 |
| AI-008 | 修改效果验证 | 用户点击“完成修改并验证” | Diff、证据覆盖变化、修改效果、安全状态、下一步 | 用户选择采用、继续修改或有风险完成 | 重构现有重评 |

## 5. AI-001 简历解析

### 输入

- 提取后的 `rawText`。
- 来源类型、文件名和解析版本。
- 支持语言：MVP 以中文简历为主，可保留英文文本。

### 输出

个人信息、教育、实习/工作、项目、校园/社团、竞赛、课程、证书、技能，以及每个字段对应的原文片段或字符范围。

### 规则

- 不推断原文不存在的经历或技能。
- 不把职责描述自动拆成已确认的个人贡献。
- 板块缺失返回空集合，不生成占位事实。
- 联系方式允许解析，但最小化展示和使用。

### 失败

Schema 失败重试当前任务；仍失败时保留原文，允许手工录入或重新上传。

## 6. AI-002 JD 解析与分类

### 输入

用户确认过 OCR 文本或直接粘贴的 JD 原文。

### 输出

- 公司、岗位名称。
- 产品细分方向及置信度。
- 是否适合应届生及不确定性。
- 主要职责。
- 岗位要求：门槛、工具方法、产品能力、协作推动、行业场景。
- 每条要求的必须/加分属性、重要程度和 JD 原文。

### 规则

- “80% 通用产品能力 + 20% 动态岗位能力”用于组织分析，不强制凑满比例。
- 无法判断时返回 `unknown` 和原因，不输出确定性结论。
- 用户修改后以用户确认版本为准。

## 7. AI-003 证据检索与匹配

### 输入

已确认岗位要求、已确认职业证据、黄色待谨慎使用证据，以及当前基础简历表达。

### 输出

每条要求的证据引用、匹配状态、证据强度、诊断、可核验理由摘要和下一步。

### 状态规则

| 状态 | 判定 |
|---|---|
| strong | 有完整任务证据或客观门槛明确满足 |
| weak_expression | 有相关事实，但简历没有体现或表达不足 |
| needs_confirmation | 可能存在相关经历，但关键角色、行动或结果未确认 |
| no_evidence | 没有相关事实，不能靠文字包装解决 |

### 禁止

- 仅因出现相同关键词判定强证据。
- 把“学习过”判定为“在业务中使用过”。
- 把团队成果默认归为个人成果。

## 8. AI-004 证据缺口追问

每次输出一个最高价值问题，包含：

- 为什么需要问。
- 对应哪条岗位要求。
- 已知事实是什么。
- 期望补充的事实类型。
- 可选“不记得/没有做过/无法证明”。

追问顺序优先：个人角色 → 关键行动/判断 → 工具方法 → 结果与数据 → 协作和困难。不得重复询问已确认信息。

## 9. AI-005 推荐表达生成

### 输入约束

只允许使用：

- 绿色已确认事实。
- 黄色事实，但必须包含贡献程度、团队性质、估算范围或项目性质。
- 当前 JD 术语，但不得借术语创造新事实。

### 输出

| 字段 | 含义 |
|---|---|
| safeText | 稳妥表达 |
| enhancedText | 可信强化表达 |
| factRefs | 支持候选表达主要经历和能力方向的事实来源 |
| requirementRefs | 对应 JD 要求 |
| rationaleSummary | 修改了什么、为什么 |
| riskFlags | 黄色证据、估算、团队成果等 |
| interviewChecks | 为什么、本人做什么、结果如何证明 |

### 表达边界

允许选择、排序、专业化措辞、动作词、真实场景化和明确协作。用户确认的准确数字可以正常使用；用户明确确认的估算数字或范围必须保留“约”“大致”“估算”等限定和风险标记。AI 推测或用户未确认的数字不得进入可采用表达。不允许虚构用户量、转化率、收入、职责、技能、证书、项目上线状态或决策权。

## 10. AI-006 三类质量审核

审核使用与生成不同的调用上下文，输入最终文本、事实来源和 JD。

### 真实性

- 每个事实是否有来源。
- 数字是否确认。
- 团队成果是否错误归因。
- 职责是否扩大。
- 技能是否有实际使用场景。

### 岗位相关性

- 核心要求是否回应。
- 关键词是否有事实支撑。
- 最相关内容是否在高关注位置。

### 表达质量

- 是否空泛、重复、过长或模板化。
- 是否说明个人行动、决策或结果。
- 是否过度使用不符合贡献程度的动作词。

无来源事实、错误个人归因和未确认数字为阻断问题。V0.1 采用“候选生成—基础格式校验—一次独立事实审核”的简化流程，审核结果统一为 `passed`、`warning`、`blocked` 和 `unavailable`。事实引用采用主要经历和能力方向级关联，不要求逐句证明；数字、个人贡献、团队成果、职责、技能和项目状态仍单独检查。

用户修改已审核的 AI 候选后不自动重新审核，结果转为用户编辑版本并移除“AI 已验证”状态；用户主动重评时交给 PF-003。

## 11. AI-007 教学反馈

输入用户自写文本、对应事实和 JD，输出：

- 已做好的地方。
- 缺失的事实或结构。
- 最多 3 条可操作修改原则。
- 是否通过真实性与相关性检查。
- 用户请求时才提供参考版本。

不得只用分数评价学习表现；保留具体行为证据。

### 11.1 AI-008 修改效果验证

AI-008 只在用户认为本轮修改完成并点击“完成修改并验证”时运行。编辑和自动保存不触发。输入上一次完成或验证文本、用户当前文本、任务最初原文、JD、已确认事实、主要来源和原审核状态。

程序先计算 Diff，并校验 Schema、数字状态和引用存在性；随后只发起一次 AI-008 语义评估，判断证据覆盖、岗位相关性、表达质量和需要语义理解的事实风险。不再为同一次验证额外调用第二个审核模型。

输出两个独立维度：

- `changeOutcome`：`improved`、`unchanged`、`regressed` 或 `tradeoff`；`tradeoff` 表示“有改善，也有新问题”。
- `safetyStatus`：沿用 PF-002 的 `passed`、`warning`、`blocked` 或 `unavailable`。

同时输出文本 Diff、证据覆盖变化、改善点、剩余问题和下一步。分数只作可选辅助信息；表达改善不得覆盖事实风险。验证失败必须保留修改前快照和用户当前文本。每次成功或失败的主动验证都追加版本化记录，页面默认展示最新结果。

## 12. Schema 与校验

1. 所有 AI 输出必须通过 JSON Schema。
2. 枚举、长度、引用 ID、分数范围和必填字段由服务端校验。
3. 引用的事实和岗位要求必须存在且属于当前用户/岗位版本。
4. Schema 失败最多自动重试有限次数；具体次数沿用当前 2 次或由技术设计确认。
5. 校验失败不得把原始模型输出直接展示给用户。

## 13. 版本与日志

每次 AI 任务至少记录：

- taskId、applicationId、userId。
- taskType、模型、温度和 token 配置。
- Prompt 版本、Schema 版本、规则版本。
- 输入对象版本引用，不在普通日志打印完整简历。
- 开始/结束时间、重试次数、状态和错误码。
- 用户是否确认、编辑或拒绝结果。

## 14. 评测体系

### 14.1 评测集

功能逻辑冻结后建立两层固定评测集：12 个端到端黄金案例覆盖 PF-001 完整链路，30 个原子安全案例分别验证数字虚构、错误归因、职责扩大、非法引用、Schema 异常和提示词注入等风险。案例使用人工构造或充分脱敏数据，不使用未经授权的真实用户数据。具体案例内容在 PF-002 功能逻辑评审后编写。

### 14.2 指标

- 事实忠实度。
- 核心要求识别准确率。
- 要求—证据匹配准确率。
- 个人贡献归因准确率。
- 建议可操作性。
- 关键词堆砌率。
- 用户二次大幅修改率。
- 专业人士盲评胜率。

### 14.3 发布门槛

- 评测集中的红色无依据事实生成必须为 0，作为 P0 阻断。
- 错误个人归因和未确认数字生成必须为 0，作为 P0 阻断。
- 其他数值阈值在评测集建立和基线测量后确认，不能在无数据时伪造。

## 15. P0 实现差距

- 当前 JD Schema 没有岗位方向、五类要求、重要度和确认状态。
- 当前简历 Schema 没有来源映射和用户确认。
- 当前分析以六维分数为中心，没有事实引用的强一致性约束。
- 当前重评估只更新分数和建议，没有保存修改前快照、用户最终文本、证据覆盖变化、PF-002 安全状态和修改效果结论。
- 当前 README 提到展示“完整思维链”，目标改为展示可核验理由摘要。
