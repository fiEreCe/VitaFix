# V0.1 开发准入评估与执行顺序

## 1. 开发准入结论

V0.1 的产品功能逻辑已经足够进入开发，但当前属于：

> 产品逻辑可开发，工程契约尚未完全可开发。

历史准入结论为 `conditional_go`。截至 2026-07-27，项目已经进入 `R1_in_progress`：

- AgentSession 状态、失败恢复、并发幂等和测试入口已经落地。
- 用户资源所有权、维护路径和旧数据迁移代码已经落地。
- PF-001 至 PF-004 仍未全部通过验收，不能进入 R2。
- 不具备公开处理真实简历的发布条件。

开发应先完成最小工程契约，再按 PF-002 → PF-001 → PF-003 → PF-004 的依赖顺序推进。

## 2. 四个 V0.1/P0 模块成熟度

| 模块 | 产品逻辑 | 当前代码基础 | 开发判断 |
|---|---|---|---|
| PF-001 证据驱动的简历优化 Agent | 主流程、分支、人工确认和停止条件已明确 | 会话、状态、任务、恢复和所有权已实现；中文匹配与事实累积未完成 | 继续完成核心追问闭环 |
| PF-002 AI 评测与安全护栏 | 运行时护栏、指标和 42 个案例已明确 | 确定性规则、结构化案例和评测入口已实现；独立语义审核未完成 | 补齐红线误放行与独立审核 |
| PF-003 修改效果验证 | 统一触发、双轴结果、风险完成和不可变记录已明确 | 已有基本验证记录和风险状态；语义判断与 handoff 未闭环 | 与 PF-002 审核一起修复 |
| PF-004 预计算引导演示 | 核心方向已明确 | 已有 `/demo` 和 fixture；真实状态契约与指标隔离未完成 | 在 PF-003 闭环后校准 |

PF-005 和 PF-006 不属于开始 V0.1/P0 开发的前置条件。

## 3. 开发前必须冻结的五项技术基线

### 3.1 V0.1 最小数据模型

现有代码以 `Resume + JD + Analysis` 和总分为中心；目标 V0.1 至少需要表达：

- Agent 会话和当前步骤。
- JD 要求及原文。
- 已确认事实及主要来源。
- 要求—证据匹配和缺口。
- 动态追问轮次、回答质量和确认结果。
- AI 候选、事实引用和 PF-002 审核状态。
- 用户采用、编辑、拒绝或跳过结果。
- PF-003 本轮基线、当前文本和不可变验证记录。

V0.1 不直接实现完整产品 MVP 的账号体系、长期职业证据库和多岗位版本管理。技术设计必须形成单次会话所需的最小模型，避免将求职作品版扩展成完整产品 MVP。

### 3.2 API 与 JSON Schema

开发前至少冻结以下接口职责：

- 创建和恢复 Agent 会话。
- 提交并确认 JD、简历输入。
- 启动分析并获取当前状态。
- 提交追问回答和确认事实。
- 生成、审核和处理候选。
- 保存用户当前文本。
- 完成修改并验证。
- 获取最新 PF-003 结果。

同时冻结 PF-001、PF-002 和 PF-003 的输入输出 Schema、枚举、引用字段、错误码、任务 ID 和幂等规则。前端不得自行推断服务端状态机。

### 3.3 Agent 服务端状态机

技术方案必须明确：

- 每个 AI 步骤是独立、可重试的任务。
- 当前状态和已确认数据由服务端保存。
- 重复请求不重复创建业务对象或消耗追问轮次。
- 失败只影响当前步骤。
- 刷新和中途退出后可按 `agentSessionId` 恢复。
- 已确认事实和用户编辑文本不能被后续失败覆盖。

### 3.4 测试与评测运行方式

仓库已经接入 Node test runner、PF-002 固定案例和 Agent/所有权回归测试。继续开发核心功能时必须：

- 已完成：接入 Node test runner。
- 已完成：将 12 个端到端案例和 30 个原子安全案例转换为结构化输入。
- 已完成：建立不调用模型的基础 Schema、数字、引用、状态和降级测试。
- 已完成：定义版本化评测结果和报告格式。
- 未完成：补齐与现有正则不同构的红线案例，并接入需要实时模型的独立审核回归。

不要求等待 42 个案例全部自动化后才开始 PF-001，但红线校验必须与核心功能同步建设。

### 3.5 PF-004 最终规格同步

开始 PF-004 前，将已经确认的以下规则写入模块规格：

- 只使用手动点击推进，不自动播放。
- 只演示一个高优先级任务的完整闭环。
- 使用“团队成果＋个人贡献＋估算数字”案例。
- 使用固定示例回答，并保留一个“没有做过”的轻量分支。
- 展示一次受控的错误归因拦截和可信修正。
- 全程显示“示例演示 · 预计算结果”。
- 使用 `sessionStorage` 保存步骤，不写数据库。
- 演示事件独立记录并带 `is_demo=true`。

## 4. 当前代码需要优先处理的风险

### 4.1 AI 重试与并发死锁风险（已解决）

原实现会在持有并发槽位时递归调用 `chat()` 重试，连续失败时内层重试可能等待外层尚未释放的槽位。

目标实现应改为：

> 获取一次槽位 → 在同一槽位内部循环有限重试 → 最终统一释放

该问题已改为在一个并发槽位内循环有限重试，并有自动化测试。后续修改 `deepseekService` 时不得恢复递归占槽重试。

### 4.2 缺少正式 JSON Schema 校验（部分解决）

当前 `chatJSON()` 只提取并解析 JSON，没有针对字段、枚举、引用和业务约束的正式 Schema 校验。PF-002 的 `passed/warning/blocked/unavailable` 以及 PF-003 的 `improved/unchanged/regressed/tradeoff` 都不能依赖前端容错。

### 4.3 异常日志可能包含完整模型输出（已解决）

JSON 解析失败日志目前只记录错误名和响应长度，不再打印完整模型文本。后续新增 AI 工具时继续遵守同一规则。

### 4.4 当前数据模型与目标功能不一致（部分解决）

旧 `Analysis` 仍以总分、雷达维度和板块分数为中心；新 Agent 链路已经使用独立 `AgentSession` 保存任务状态、事实引用、候选和 PF-003 基本验证记录。PF-003 完整语义结果和 handoff 仍未闭环。

旧 `Analysis` 可以继续作为迁移来源和历史兼容对象，不应再通过持续增加可选字段代替 AgentSession 的领域边界。

### 4.5 所有权校验不完整（代码已解决，迁移待运行）

JD、Resume、Supplement、Analysis 和 AgentSession 的用户路径、异步写回、cleanup 和迁移维护路径已经加入所有权约束。旧数据迁移工具已实现；在任何公开处理真实材料前，仍必须完成真实 MongoDB dry-run、冲突审查、正式迁移和 Supplement 索引验证。

## 5. 不阻塞 V0.1 开发的事项

以下事项属于后续产品 MVP 或更晚版本，不阻塞当前开发：

- 正式账号、登录和跨设备同步。
- 长期职业证据库。
- 免费账号 30 天保留。
- 导入导出和迁移。
- PDF/Word 高质量排版。
- 收费、会员、支付和自动投递。
- PF-005 健康度体检和 PF-006 面试预测/多版本改写。

非红线 AI 指标的具体数值门槛也不阻塞开发；它们在首轮基线评测后冻结，但会阻塞最终求职验收。

## 6. 推荐开发顺序

```text
S0 开发基线冻结
  ↓
S1 PF-002 确定性校验与测试框架
  ↓
S2 PF-001 最小 Agent 会话和一个高优先级任务闭环
  ↓
S3 候选生成与 PF-002 运行时审核
  ↓
S4 PF-003 修改效果验证
  ↓
S5 从真实闭环生成版本化 fixture
  ↓
S6 PF-004 预计算引导演示
  ↓
S7 完整评测、回归和求职验收
```

不得先单独开发 PF-004。PF-004 必须复用 PF-001 至 PF-003 已落地的真实状态结构。

## 7. 各阶段退出条件

### S0 开发基线冻结

- V0.1 最小领域对象和状态图明确。
- API、Schema、错误和幂等规则明确。
- 测试运行器和目录结构确定。
- PF-004 已确认细节同步完成。

### S1 PF-002 基础设施

- Schema 校验可执行。
- 数字、引用、归因状态和非法枚举有自动测试。
- 结构化案例格式和评测结果格式确定。
- AI 调用的重试、并发和日志风险修复。

### S2—S3 PF-001 纵向闭环

- 至少一个高优先级任务真实跑通。
- 证据不足会追问，明确没有经历会标记能力缺口。
- 候选只使用已确认事实。
- 候选通过 PF-002 后才进入用户确认。
- 刷新、失败和重试不丢失已确认事实。

### S4 PF-003

- 用户完成一轮修改后统一验证。
- Diff、证据覆盖、修改效果和安全状态可展示。
- 一次验证只调用一次语义评估。
- 每次验证追加不可变记录。
- `blocked` 内容只能以 `completed_with_risk` 完成。

### S5—S6 PF-004

- fixture 来自真实闭环状态。
- 手动演示覆盖追问、确认、护栏和修改验证。
- 不调用实时 AI，不写普通历史。
- 30 秒内看到第一次明确价值。

### S7 求职验收

- PF-001 至 PF-004 达到 `verified`。
- 固定案例、红线指标、失败案例和至少一次回归对比完成。
- 可部署构建、引导演示、Agent 图和评测报告可用。

## 8. 下次执行起点

下次继续开发时，不再从 S0 重复开始。按以下三个批次推进：

1. PF-001：中文证据匹配、回答质量、事实合并、动态问题和失败重试。
2. PF-002/PF-003：独立语义审核、数字用途、安全状态、修改效果、最终文本和 handoff。
3. PF-004/收口：真实 fixture 契约、演示指标隔离、前端错误展示、完整评测和生产构建。

旧数据迁移作为部署前操作单独执行，不阻塞本地继续修复 PF-001，但会阻塞公开处理真实数据。详细状态和命令见 [开发交接文档](./11-development-handoff-2026-07-27.md)。
